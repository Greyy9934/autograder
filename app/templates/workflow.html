END-TO-END EVALUATION WORKFLOW
System Architecture Sequential workflow / evidence-driven

How a submission moves through the evaluator

The evaluator follows one ordered workflow. Each phase consumes the previous phase's outputs and produces evidence for the next. AI agents perform specialized reasoning; deterministic software performs validation, execution, scoring and report generation.

PHASE 01 — SUBMISSION INTAKE AND STATIC INSPECTION

Performed by: Intake and static-analysis software

Input: C source file and submitted problem statement, if provided.

Operations:

  • Validate source presence, size and basic structure.
  • Inspect headers, dependencies, declarations and functions.
  • Analyze variables, loops, recursion, arrays and pointers.
  • Inspect input/output handling, memory operations and unsafe functions.
  • Identify suspicious arithmetic, integer and control-flow patterns.
  • Estimate preliminary complexity indicators and record source locations.

Output: Validated submission, source fingerprint and structured static-analysis findings.

Gate: Invalid or unusable submissions stop here. Static findings are not proof of defects.

PHASE 02 — PROBLEM RECONSTRUCTION

Performed by: Agent 1 — Problem Understanding

Input: Submitted problem statement, source code and static-analysis evidence.

Operations:

  • Reconstruct the intended task and expected behavior.
  • Identify input format, output format and constraints.
  • Separate explicitly stated facts from assumptions.
  • Identify ambiguity, missing requirements and contradictions.
  • Ask targeted clarification questions when the specification is incomplete.
  • Report confidence and limitations.

Output: Structured assignment-specification draft and clarification requirements.

Gate: An incomplete or ambiguous specification cannot proceed to reference generation.

PHASE 03 — INSTRUCTOR REVIEW AND SPECIFICATION APPROVAL

Performed by: Instructor approval workflow and deterministic validation software

Input: Agent 1's specification draft and its evidence.

Operations:

  • Present the reconstructed task, formats, constraints and assumptions for review.
  • Allow the instructor to correct or clarify the specification.
  • Validate the final specification and calculate its fingerprint.
  • Record explicit instructor approval.

Output: Immutable, confirmed assignment specification and approval evidence.

Gate: No confirmed specification means no reference generation or specification-dependent test generation.

PHASE 04 — REFERENCE SOLUTION GENERATION AND VALIDATION

Performed by: Agent 2 — Reference Solution Generator, followed by deterministic validation software

Input: Confirmed assignment specification.

Operations:

  • Generate a straightforward or brute-force reference implementation.
  • Generate an efficient reference implementation where appropriate.
  • Explain the algorithm, assumptions, time complexity and space complexity.
  • Check generated implementations against the approved specification.
  • Use independent reasoning, instructor examples and exhaustive small cases where feasible.
  • Record the provenance and validation limitations of each reference.

Output: Reference implementations, explanations and validation records.

Gate: An unvalidated AI-generated reference is not automatically trusted as a correctness oracle. Its permitted use must be recorded.

PHASE 05 — TEST DESIGN AND GENERATION

Performed by: Agent 3A — Random Test Generator; Agent 3B — Adversarial Test Planner; deterministic test-validation software

Input: Confirmed specification, input constraints, student source and available reference solutions.

Operations:

  • Agent 3A generates reproducible random inputs using explicit schemas, seeds and distributions.
  • Agent 3B examines the submitted implementation for likely failure conditions.
  • Design edge cases for boundaries, empty and singleton inputs, duplicates, ordering assumptions and maximum constraints.
  • Target likely implementation defects such as off-by-one errors and integer overflow.
  • Validate generated inputs against the approved input schema.
  • Record test rationale, expected behavior and source locations of suspected weaknesses.

Output: Validated random-test batches and prioritized adversarial test plans.

Gate: Test proposals are not test failures. They must be executed before conclusions are drawn.

PHASE 06 — ISOLATED EXECUTION AND DETERMINISTIC VERIFICATION

Performed by: Secure execution subsystem and deterministic comparison software

Input: Student source, validated test inputs, confirmed specification and eligible reference implementations.

Operations:

  • Compile programs inside the configured isolated execution environment.
  • Run student and eligible reference programs against the same inputs.
  • Capture standard output, standard error, exit codes and resource usage.
  • Apply execution time, memory, process and output limits.
  • Compare outputs using the configured comparison rules.
  • Classify passing, failing and inconclusive outcomes separately.
  • Preserve execution logs and reproducible failure evidence.

Output: Compilation records, execution evidence, test outcomes and differential-comparison results.

Gate: Infrastructure errors are not student failures. Untrusted references cannot independently establish incorrectness.

PHASE 07 — COMPLEXITY, CORRECTNESS AND CODE-QUALITY ASSESSMENT

Performed by: Agent 4, Agent 5, Agent 6 and supporting analysis software

Input: Original submission, approved specification, static findings and available execution evidence.

Agent 4 — Complexity Analysis:

  • Derive theoretical time and auxiliary-space complexity.
  • Examine loops, recursion, data structures and dominant operations.
  • Measure runtime over controlled input sizes and distributions.
  • Compare growth ratios and fit candidate complexity models.
  • Present theoretical and empirical results with graphs and limitations.

Agent 5 — Mathematical Correctness:

  • Examine algorithm logic, preconditions and postconditions.
  • Review loop invariants, induction arguments and proof obligations.
  • Search for counterexamples and unsupported assumptions.
  • Classify conclusions as proved, proof-reviewed, unproven, disproved or inconclusive.

Agent 6 — Code Quality and Feedback:

  • Assess readability, modularity, organization and maintainability.
  • Review implementation choices and code structure.
  • Identify originality or similarity signals for human investigation.
  • Produce source-linked explanations and actionable improvements.

Output: Three separate assessment records with supporting evidence, reasoning and limitations.

Gate: An empirical trend is not a proof; an AI proof sketch is not automatically a verified proof; similarity is not proof of plagiarism.

PHASE 08 — DETERMINISTIC GRADING AND FINAL REPORT

Performed by: Grading engine, report-generation module and orchestration software

Input: All eligible evidence and assessment records from the preceding phases.

Operations:

  • Check evidence completeness, provenance and scoring eligibility.
  • Apply the configured grading rubric and deterministic scoring rules.
  • Exclude unsupported or inconclusive evidence from inappropriate score calculations.
  • Distinguish provisional results from eligible final grades.
  • Assemble the specification, references, static findings, test results, complexity analysis, correctness review and code-quality feedback.
  • Generate a downloadable PDF with consistent content, evidence and score breakdown.

Output: Evaluation result, score breakdown, evidence-linked feedback and final PDF report.

Completion condition: A final grade is issued only when the required evidence and grading eligibility conditions are satisfied. Otherwise, the result remains provisional or inconclusive.

ARCHITECTURE RULE: The orchestrator coordinates the eight phases and enforces dependencies. Agents 1–6 are AI reasoning components. Static analysis, approval validation, reference validation, test validation, execution, comparison, grading and PDF generation are software subsystems—not additional AI agents.
